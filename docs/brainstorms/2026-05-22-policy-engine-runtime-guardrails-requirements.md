# Policy Engine — Runtime Guardrails for Agents and Orchestrator

## Problem Frame

The marketplace today has a `/governance` page ([apps/web/app/governance/page.tsx](../../apps/web/app/governance/page.tsx)) that renders mock approval requests, audit logs, and policy rows — but there is no backing data model, no policy CRUD, no lifecycle, and no toolkit-shape policy enforcement anywhere in the platform. (An unrelated in-tree engine at [apps/api/src/lib/policy/engine.ts](../../apps/api/src/lib/policy/engine.ts) covers rate-limit / model-allowlist / cost-budget / human-gate verbs against a different Zod schema; how it coexists with the new toolkit-shape engine is a P0 under "Resolve Before Planning".) Agents published into the catalog and workflows run on the orchestrator canvas can call any tool, invoke any model, and emit any prompt/output with no runtime protection from toolkit-style guardrails.

Meanwhile, the sibling repo [agent-governance-toolkit](../../../agent-governance-toolkit) ships 11+ curated YAML policy templates (PII detection, prompt-injection safety, MCP security, SQL safety, semantic intent classification, sandbox safety, conversation guardian, CLI security, ADK governance, etc.), each with a disclaimer marking it a sample to be customized for production. The 11 YAMLs do not all share one schema; the formal `PolicyDocument` JSON Schema at `agent-governance-toolkit/packages/agent-os/src/agent_os/policies/policy_schema.json` matches only the `examples/policies/production/*.yaml` shape — a fact that shapes the cut in this v1.

We want to close that gap: a first-class **policy engine** that lets tenants import these toolkit policies, manage their lifecycle in the marketplace, and have them enforced at runtime by every published agent and every orchestrator workflow they explicitly attach a policy to. Enforcement — not publish-time admission — is the primary value: a published agent must not be able to leak PII, accept a prompt-injection payload, or run a destructive SQL command without the central decision point seeing and ruling on the request.

## Requirements

**Policy catalog & authoring**
- R1. A new `/policies` area in the marketplace surfaces a catalog of policies for the current tenant, with filtering by status (Draft, Published), category (e.g., pii, prompt-injection, mcp, sql), and free-text search by name/description.
- R2. Authors can create a new policy by either (a) importing one of the seeded toolkit YAML templates and forking it under a tenant name, or (b) starting from a blank policy with the `PolicyDocument` schema scaffolded.
- R3. The authoring view is a YAML editor with live schema validation against the formal `PolicyDocument` schema (`agent-governance-toolkit/packages/agent-os/src/agent_os/policies/policy_schema.json`, the shape used by `examples/policies/production/*.yaml`). Seeded baseline policies (R16) that use other toolkit shapes are presented read-only in the editor in v1; editing them as YAML is deferred until per-shape validators exist.
- R4. Each policy has tenant-scoped metadata: id, name, description, category tags, owner, created/modified timestamps, version label, and current status.

**Lifecycle (two-state)**
- R5. Every policy is in exactly one of two states: `Draft` or `Published`. Drafts are editable; Published policies are immutable in place — to change a Published policy the author creates a new Draft (e.g., by duplicating it), edits, and publishes.
- R6. The Publish action is gated by a `policy-publisher` role (separation from `policy-author`). The act of publishing is the approval — there is no separate review state in this iteration. If the Draft being published carries a non-empty `disclaimer` field (every seeded toolkit policy does), the Publish dialog displays the disclaimer text verbatim and requires explicit checkbox acknowledgement; the acknowledgement (actor, timestamp, disclaimer hash) is captured in the R8 audit entry.
- R7. A policy can be Unpublished (returned to Draft) only if no agent or workflow is currently bound to it; the UI must list active bindings and require the user to detach them first. Detach actions originate in the policy view's Bindings tab.
- R8. Every transition (Draft created, edited, Published, Unpublished) writes an audit log entry with actor, timestamp, policy id + version, and a short reason field.

**Binding to agents and orchestrator (workflow-root only in v1)**
- R9. When a publisher registers (or edits) an agent in the marketplace, they explicitly select zero or more Published policies to attach. The attached policy ids and pinned versions travel with the agent's manifest. The asset detail view shows the pinned version of each attached policy.
- R10. When a user designs an orchestrator workflow, the workflow root can have zero or more Published policies attached. Per-node binding is out of scope for v1. Policies are stored on the workflow definition (not derived from the agents inside it), so an orchestrator workflow can add stricter policies on top of an agent's own bound set.
- R11. The marketplace UI for agents and for orchestrator workflows shows which policies are currently attached and the pinned version of each. Stale-pin (version-drift) warnings, "upgrade to latest" affordances, and tenant-wide migrations are out of scope for v1.
- R12. Enforcement scope is exactly the union of policies that agents/workflows explicitly attached — subject to the **default-binding posture** decision under "Resolve Before Planning" (which may add a small tenant-baseline floor before v1 ships).

**Central Policy Decision Point (PDP)**
- R13. The marketplace exposes a single Policy Decision API (a new Azure Function under `apps/api`) that takes a decision request — caller identity (agent id or workflow id), action context (tool call, model call, prompt-in, prompt-out), and the payload to evaluate — and returns a decision. The caller's tenantId is derived from the authenticated principal (see Resolve Before Planning), never from the request body.
- R14. The PDP loads the set of policies bound to the caller, evaluates every rule in every bound policy against the payload, and returns a single decision response: overall verdict, list of matched rules (policy id, rule id, severity, explanation), and the aggregated redacted payload when applicable. When multiple matched rules redact the same field, redactions apply in deterministic order (by policy id, then rule id) and each rule operates on the output of the prior; redaction is idempotent.
- R15. Supported enforcement action verbs the PDP returns per matched rule in v1: `allow`, `block`, `warn`, `redact`. The overall verdict is the most restrictive of the matched rules (block > redact > warn > allow). Toolkit rules expressing other verbs (`transform`, `require-approval`, `escalate`) are imported and stored verbatim but downgraded to `warn` at evaluation time in v1; the original verb is preserved in the audit record so future versions can promote without re-importing.
- R16. Every decision (including `allow`) writes an audit record (PDP request id, caller id, bound policy ids + versions, matched rule ids, verdict, latency ms) for later observability. Raw or redacted request payloads are not persisted in v1; reconstruction of what was evaluated relies on rule ids + caller context.

**Seeding**
- R17. On first tenant initialization, the marketplace seeds the tenant's policy catalog with a curated baseline of 4 toolkit policies (`pii-detection`, `prompt-injection-safety`, `mcp-security`, `sql-safety`) as `Draft` entries owned by a system user. The remaining toolkit policies are available via the R2 import flow but are not auto-seeded in v1.
- R18. Each seeded Draft preserves the baseline policy's original `name`, `version`, `disclaimer`, and rule body verbatim, plus a `source` field carrying the upstream toolkit path and a pinned git SHA. Seed files are hash-checked against a checked-in manifest at seed time; any drift fails seeding loudly.
- R19. Seeding runs exactly once per tenant on first initialization. Re-running seeding on an already-seeded tenant is rejected with a clear error. Idempotent re-seed and admin-triggered Sync-from-toolkit are deferred.

## Success Criteria

- An admin can complete the loop end-to-end: open a seeded `pii-detection` Draft, publish it (acknowledging its disclaimer), attach it to a registered agent, send a tool call carrying obvious PII through the agent, and see the PDP return a `redact` verdict with the redacted payload in the response and a matching audit record — without writing code.
- The `/policies` page shows the 4 seeded baseline policies (PII, prompt-injection, MCP security, SQL safety) as Drafts on tenant initialization, reachable within one click of the marketplace home.
- An orchestrator workflow can attach a stricter set of policies at its root than its constituent agents have bound, and the runtime decision for a call inside that workflow honors both sets.
- A Published policy cannot be silently edited; any change is forced through a Draft → Publish cycle and produces an audit entry the governance page surfaces.
- The PDP returns a decision for a typical tool-call payload (<8 KB) bound to the 4 baseline policies in under 100 ms p95 with warm policy cache, and under 500 ms p99 with cold cache, on local dev. Production latency and availability targets are revalidated in v1.1 once load-test infrastructure exists.

## Scope Boundaries

- **Out:** publish-time admission gating. Asset publishing is unaffected; `mkt-00009` does not call the PDP in this iteration.
- **Out:** separate "In Review" approval state, multi-step approval workflows, immutable-versioned releases with channel pinning. Lifecycle is intentionally two-state (Draft → Published) for v1.
- **Out:** `transform` and `require-approval` action verbs and their associated approval-wait protocol. Imported toolkit rules expressing them are stored and downgraded to `warn` per R15. Deferred to v1.1 once the block/warn/redact loop is in production.
- **Out:** per-node policy binding inside an orchestrator workflow. Workflow-root binding only in v1.
- **Out:** version-drift warning indicator on attached policies (the rejected original R11). Pinned version is shown per R11 but stale-pin warnings, "Upgrade to latest" affordances, and tenant-wide migration of pinned versions are deferred.
- **Out:** persisted request/response payloads in the audit store. Audit holds metadata only (rule ids + verdict + caller). Payload-level audit and its associated redaction story are deferred.
- **Out:** idempotent re-seeding and admin-triggered Sync-from-toolkit. Initial-seed-only in v1; a re-seed attempt is rejected with an error.
- **Out:** in-agent SDK enforcement. Agents call the central PDP service over HTTPS; we do not ship or embed the agent-governance-toolkit SDK inside agent runtimes in this iteration. Short-lived, offline, batch, and edge agents that cannot reliably reach the PDP on every call are explicitly unenforced in v1; their catalog entries display a `runtime guardrails: not available` badge so the gap is visible to publishers and consumers.
- **Out:** policy authoring beyond YAML. No form-based authoring, no drag-and-drop rule builder, no natural-language policy generator in v1.
- **Out:** policy distribution to external (non-marketplace) agent runtimes. The PDP is reachable from anything that can call the API, but no SDK, no signed bundle, no offline cache is shipped.
- **Out:** simulation / what-if / shadow-mode testing of a Draft policy against historical traffic. Deferred.

## Key Decisions

- **Runtime guardrails over publish gating** — Enforcement is where the user said the value lives, and where the marketplace's current mock UI has the largest gap. Tying policies to `mkt-00009`'s asset submission pipeline can layer on later.
- **Path A scope cut after document-review** — v1 ships the smallest end-to-end loop that delivers the PII-redact demo: 4 seeded baseline policies, workflow-root binding only, 4 action verbs (allow/block/warn/redact), no per-node binding, no version-drift UI, no payload-level audit, no idempotent re-seeding. Each cut originated from a reviewer finding; the deferred surface is enumerated under Scope Boundaries so nothing is silently dropped.
- **Central PDP service over in-agent SDK** — One audit trail, one place to update policies live, language-agnostic enforcement. The 5–30 ms network hop is acceptable for v1 inside the same Azure region. Offline/edge/batch agents are explicitly out of v1 enforcement and surfaced as such in the UI; that gap is acknowledged, not papered over.
- **YAML editor scoped to the production schema** — v1 authors only against the formal `PolicyDocument` schema (`examples/policies/production/*.yaml` shape). The other toolkit shapes (`builtin_patterns`, `detection_patterns`, `signals`, `sql_policy`, `adk_governance`) are seeded as informational Drafts the PDP can evaluate via per-shape interpreters, but the editor presents them read-only. Full editing of those shapes is deferred until per-shape validators exist.
- **Two-state lifecycle (Draft → Published)** — Simplest model; publishing is the approval. **Known compliance gap (called out, not hidden):** if a single person holds both `policy-author` and `policy-publisher` roles, the model does not provide real separation of duties. v1 is acceptable for the demo/preview surface; regulated tenants need the `In Review` state added before sign-off (additive change). The doc does not claim SoD as a v1 security feature.
- **Workflow-root binding only in v1** — Satisfies the success criterion ("workflow attaches stricter set than its agents") without the per-node React Flow side panel, per-node badge contract, root+node aggregation rules, and cross-container detach-check fan-out that per-node binding implies. Per-node binding is deferred to v1.1 once root-binding UX is in front of users.
- **Action verbs narrowed to 4** — `allow / block / warn / redact` cover the PII-redact, prompt-injection-block, MCP-security-warn, and SQL-block demo paths. `transform` and `require-approval` add disproportionate v1 surface (replacement-template schema superset, approval-wait protocol, approval-resolution UI on top of a `/governance` page that is currently mocked). Imported toolkit rules expressing them are preserved verbatim and downgraded to `warn` for evaluation, so v1.1 can promote without re-importing.
- **Seed 4 baseline policies as Drafts** — The success criteria only require 4. Seeding 11 multiplies schema-validation risk against unverified shapes and produces a triage queue admins won't process. Baseline-as-Draft (not Published-by-default) is a conscious trade-off versus the product-lens recommendation to ship a 2-policy baseline as Published; that recommendation is folded into the default-binding posture decision under "Resolve Before Planning" because the same answer covers both.
- **`/policies` replaces the policy section of `/governance`** — `/governance` is restructured to host Approvals + Audit Logs only, with a "Manage policies →" link to `/policies`. The existing three-state mock (active/draft/disabled) is replaced wholesale by the two-state model in R5; no migration of the mock `disabled` status.
- **Acknowledge the existing in-tree engine, don't pretend it isn't there** — `apps/api/src/lib/policy/engine.ts` already implements a different policy surface (Zod schema, verbs `allow|deny|transform|pending-approval`, types like rate-limit/cost-budget/human-gate). v1 keeps it in place for those existing use cases; the new engine owns the toolkit-shape runtime-guardrails surface. A unification path (which engine wins which use case, on what timeline) is a P0 under "Resolve Before Planning" — running two engines indefinitely is rejected.
- **Cross-cutting v1 hardening floor** — YAML safe-loaders only, regex compiled with a re2-class engine plus per-rule wall-clock timeout, baseline non-overridable audit redactor for any future payload-level audit. Bundled as one P0 under "Resolve Before Planning" because they share an implementation pass and a security review.

## Dependencies / Assumptions

- The agent-governance-toolkit's formal `PolicyDocument` JSON Schema (`packages/agent-os/src/agent_os/policies/policy_schema.json`) is stable enough to be vendored at a pinned git SHA and used as the v1 authoring schema. The 4 baseline YAMLs (`pii-detection`, `prompt-injection-safety`, `mcp-security`, `sql-safety`) each use a different top-level shape from `PolicyDocument` and are seeded as read-only Drafts the PDP evaluates via per-shape interpreters; the planning pass enumerates the interpreters needed (one per baseline shape). _Spot-check the 4 baseline shapes before planning sign-off._
- Bound policy enforcement requires agents and orchestrator workflows to actually call the PDP at the right moments (before tool invocation, before model call, on prompt-in, on prompt-out). The agent runtime and orchestrator runtime changes (touching at minimum `apps/api/src/functions/sessions/sessions.ts`, the workflows runtime, and the agent execution path) are inside this engine's scope; the precise hook points are enumerated in planning. _Unverified during brainstorm._
- Cosmos DB is the persistence layer per project conventions (tenantId partition key). Policies, bindings, and audit decisions become Cosmos containers; the existing `governance` API surface and Cosmos schemas can extend rather than fork. A denormalized `policy-bindings` container (partitioned by `policyId`) is the assumed answer to R7's detach-check fan-out — confirmed in planning. _Inferred from CLAUDE.md._
- Toolkit YAMLs reach Azure Functions at runtime via build-time vendoring (copy a pinned commit of `agent-governance-toolkit/examples/policies/` into `apps/api/policies/seed/` at build) — the path is not currently a dependency of `apps/api`. _Implementation detail confirmed in planning._
- Existing mock `/governance` page is acceptable to repurpose (its current rows become real data sourced from this engine); the three-state policy mock is replaced wholesale, not migrated.
- Sprint 2 backlog items `mkt-00009` (asset submission with policy checks) and `mkt-00011` (governance approval workflow with Azure Confidential Ledger) are coordinated explicitly with this engine: `mkt-00009` is the v1.1+ candidate consumer of the PDP for publish-time admission; `mkt-00011`'s Confidential Ledger is the candidate immutable backing store for the R8/R16 audit streams. Deeper integration scoping is deferred to planning. _Stated, not yet committed._

## Outstanding Questions

### Resolve Before Planning

Six P0 items surfaced by the document-review pass (adversarial + security-lens + product-lens + feasibility). Each is a blocker for safe planning; the recommended baseline for each is given so a user answer can be a short confirm/deviate rather than a full redesign.

- [Affects R13, R14, all callers][Architecture] **PDP fail-mode contract.** What does an agent or orchestrator do when the PDP times out, returns 5xx, or is unreachable? Fail-open silently disables every guardrail (contradicts the problem-frame promise); fail-closed turns a PDP outage into a tenant-wide agent outage. **Recommended baseline:** fail-closed for any rule with verb `block`, fail-open + log + continue for `warn`/`redact`, contract enforced at the PDP/SDK boundary not at the caller, with a per-tenant override role-gated separately. Add a v1 availability target (recommend 99.9% local-dev, revalidated for production in v1.1) alongside the latency target.
- [Affects R13, all][Security] **PDP authentication, tenant isolation, and principal binding.** How is the calling agent/workflow authenticated? **Recommended baseline:** Entra ID managed identity / workload identity per caller; the PDP rejects any call without a token; tenantId is derived from token claims (never the request body); the asserted agent_id/workflow_id is cryptographically bound to a claim issued at agent registration so a less-restricted agent cannot impersonate a stricter one within the same tenant. Without this, the PDP is an open IDOR + cross-tenant probe surface (OWASP A01/A07).
- [Affects R6, R8, Key Decisions][Security] **`policy-publisher` role source and SoD posture.** Where do roles live (Entra app role recommended, Cosmos as cache)? What is the role-to-action matrix (`policy-author`, `policy-publisher`, future approval-resolver)? Does v1 enforce two distinct humans for author and publisher, or honestly document the SoD gap? Until this is answered, R6 is decorative.
- [Affects R9, R10, R12, R17, Key Decisions: "Seed 4 baseline"][Product] **Default-binding posture (covers the zero-bind question and the seed-as-Published question together).** Three options: (a) tenant baseline (`pii-detection` + `prompt-injection-safety`) is auto-bound on agent registration with explicit opt-out + justification captured to audit (Defender/Purview pattern; matches the product-lens "ship safety baselines on by default" argument); (b) zero-policy publish is hard-blocked unless the publisher writes "no runtime guardrails — accepted risk" into the audit log; (c) explicit-binding-only with a first-class success metric (`% of Published agents with ≥1 PII or prompt-injection policy bound`) so the gap is measured. The doc's current implied default (non-blocking warning) was identified by adversarial + product reviewers as the worst of all options. **Recommended baseline:** option (a), because it preserves the demo loop while removing the silent-under-protection failure mode.
- [Affects Problem Frame, all][Architecture] **Disposition of existing `apps/api/src/lib/policy/engine.ts`.** Three options: (a) deprecate and remove in this iteration, migrating its rate-limit / model-allowlist / cost-budget / human-gate verbs into the new schema; (b) keep it for the legacy verbs only, declare the new engine as the toolkit-shape surface, document the boundary explicitly so the two engines don't collide on URL space, Cosmos containers, or developer mental model; (c) port its verbs into the new engine over v1.1–v1.2 with a clear deprecation timeline. Pick before planning — "two engines forever" is rejected.
- [Affects R3, R13, R14, R16][Security & Operability] **Cross-cutting v1 hardening floor.** Three guardrails the doc commits to as a single bundle: (a) YAML loaders restricted to safe loaders (`yaml.safe_load` equivalent, anchor-expansion bounds, doc-size cap) everywhere YAML is read — editor, import, seeder; (b) regex patterns compiled with a linear-time engine (re2-class), per-rule wall-clock timeout that produces a defined `rule-timeout` verdict (never silently degrades to `allow`), per-request evaluation budget; (c) a baseline non-overridable redactor (PII patterns + secret patterns + large-payload hashing) that applies to any error metadata, trace, or future payload-level audit so audit safety never depends on per-policy authoring quality. Bundled because they share one implementation pass and one security review. **Recommended baseline:** accept all three.

### Deferred to Planning

- [Affects R3][Technical] Where the YAML schema validator lives — a shared package consumed by both the editor and the PDP, or duplicated client/server. Likely shared package.
- [Affects R13, R14][Technical] Whether the PDP is a single Azure Function endpoint or splits decision / audit / management into separate functions. Likely single decision endpoint + separate management endpoints.
- [Affects R13, R16][Technical] Whether the decision endpoint emits a synchronous response or also exposes an async/event channel for the audit emit so audit writes don't sit on the decision latency budget. Likely fire-and-forget audit via Cosmos change feed or Service Bus.
- [Affects R7][Technical] Cross-container index strategy for the "detach before unpublish" check — almost certainly a denormalized `policy-bindings` container partitioned by `policyId` that agent/workflow write paths maintain.
- [Affects R14, R15][Technical] Per-shape interpreter inventory for the 4 baseline policies (regex-pattern for `pii-detection`, regex + encoded-payload for `prompt-injection-safety`, categorized-pattern for `mcp-security`, blocked-statement for `sql-safety`) plus a decision on which interpreter `PolicyDocument` policies authored in the editor use.
- [Affects R16][Technical] Audit retention default (recommend 90 days hot in Cosmos, archive to Blob), partition key strategy (recommend `tenantId + date-bucket`), and sampling of `allow` verdicts in high-traffic tenants.
- [Affects R3, R9][Technical] Concrete UI choices: YAML editor component (CodeMirror 6 recommended over Monaco for bundle size + a11y), policy picker pattern (shadcn `Command` + `Popover` Combobox with paginated server-side search), where R7's detach mutations physically live.
- [Affects cross-cutting][Technical] Accessibility commitments (WCAG 2.1 AA for `/policies` and the picker; keyboard-only authoring with `Esc`-to-exit-trap in the YAML editor; aria-live announcement of validation errors). Likely added to a separate "NFR" section in the plan.
- [Affects cross-cutting][Technical] Responsive scope — `/policies` authoring desktop-only (≥1024px); catalog browse, attached-policies view, and approvals inbox responsive to 768px so reviewers can act from a tablet.
