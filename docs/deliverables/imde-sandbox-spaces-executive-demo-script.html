1 Demo contract

  • Scenario: imde-rcm-denial-demo
  • Audience: Executive review
  • Target duration: 15 minutes
  • Data posture: All visible data is synthetic, de-identified, simulated, or approved demo data.
  • Live-service posture: Request, approval, lifecycle, publish, and projection records use app flows where practical. AML provisioning, notebook execution, and training/evaluation are deterministic demo projections unless a live workspace has been prevalidated.
Real backend records Deterministic projections No live PHI No live training

2 End-to-end flow

Five stages — Request · Approve · Build · Publish · Consume — across four lanes (actors, marketplace UI, marketplace API, backing services). The UAP Hub is an external dependency: the base model id is resolved when the sandbox is registered, then fine-tuning runs inside the tenant's Azure ML workspace.

Reading the diagram: top-to-bottom inside each stage shows the request path (actor → UI → API → backing service); dashed left-to-right arrows show the handoff between stages along the UI lane. The Build stage has no marketplace API call — notebook and experiment work happens directly against the provisioned Azure ML workspace and surfaces back into the marketplace only at the Publish step.

3 Starting state

  1. Check out branch feat/imde-modernization.
  2. For the deterministic backend path, set UAP_ENABLE_IMDE_DEMO=true and AZURE_FUNCTIONS_ENVIRONMENT=Development in the API env (the latter enables actorId-based auth for reset/approve/publish without an admin token).
  3. If you need a pre-publish baseline, clear the browser local publish marker: 
    localStorage.removeItem("imde-demo-model-experience")
  4. Reset the canonical scenario (API running locally): 
    POST /api/sandboxes/demo/reset
Content-Type: application/json

{
  "tenantId": "default",
  "demoScenarioId": "imde-rcm-denial-demo",
  "actorId": "presenter-admin"
}

→ 200 {
  "tenantId": "default",
  "demoScenarioId": "imde-rcm-denial-demo",
  "deleted": {
    "lifecycleEvents": N,
    "submissions": N,
    "modelExperiences": N,
    "sandboxes": N
  }
}
    When UAP_IMDE_DEMO_ADMIN_TOKEN is configured, include the x-imde-demo-admin-token header.
Goal of reset: demo sandboxes, lifecycle events, sandbox-sourced submissions, and the Published Model Experience projection return to baseline. Unrelated tenant and non-demo records are untouched.
Live Azure is not required. Request, approval, publish, and the model experience are all deterministic projections. A missing AML compute instance, locked-down storage, or absent publicNetworkAccess does not block any of the 8 routes.

5 Presenter notes

  • Do not describe the demo as live training. Use this language: “The training and evaluation results are deterministic demo projections so we can focus on the governed workflow.”
  • Call out the two approval moments separately:
    • Platform admin approves the sandbox — compute, data, and team.
    • Model governance passes during publish, before the marketplace experience appears.
  • When showing /models, emphasize that this is not a separate public Spaces product. It is a Spaces-like experience inside the existing enterprise Models marketplace.
  • Keep PHI language out of typed fields. Use synthetic claim examples only.

When validating end-to-end without driving the UI. Two actor roles matter:

Payload gotchas:
  • amlModelVersion must be a positive integer string ("1", not "1.0.0").
  • The publish body field is trainingRunId, even though the UI URL exposes it as ?runId=….
  • Only run-denial-pubmedbert-v3 is accepted as the selected winner; any other id returns 400.

7 Smoke checklist

Use this as a pre-rehearsal pass — checkboxes are interactive in the browser.

  • Reset canonical scenario and clear the local publish marker.
  • Open /sandbox; the executive demo card appears.
  • Submit the demo request and land on sandbox detail.
  • Approve the sandbox; verify ready state, approval reason, lifecycle events, data statement, and next actions.
  • Open notebook and experiments from the sandbox detail page.
  • Verify the selected run is run-denial-pubmedbert-v3 and the publish action is available.
  • Publish from /imde/push; success state includes a marketplace link.
  • Open /models/rcm-denial-prediction-space; runnable preview, metrics, lineage, and governance evidence render.
  • Return to /models; the Published Model Experience card shows preview and governance badge.
  • Reset again; backend demo records are removed and the browser-local publish marker is cleared for the next rehearsal.

8 Accessibility & display checks

  • Desktop / projector: no card text overlaps at 1366px width.
  • Narrow window: primary actions remain visible without horizontal scrolling.
  • Keyboard: request submit, approval, notebook / experiments / publish links, and the model preview actions are focusable.
  • Screen reader: status badges, the approval button, the publish button, and the model preview button have readable visible labels.

9 Healthy signals

  • sandbox-demo.test.js passes.
  • API build passes.
  • Publish response includes submissionId, projectionId, modelRouteId, and modelRoute.
  • Model detail route resolves to /models/rcm-denial-prediction-space.
