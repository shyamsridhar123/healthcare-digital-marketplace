Updated Communication Design: Direct Calls vs. Event Hub in Global Orchestration
Default Approach: Direct Orchestrator-to-Orchestrator Calls
In our Global Agentic Orchestrator architecture, the Global Orchestrator triggers Domain Orchestrators using direct API calls via the Agent-to-Agent (A2A) protocol (typically an HTTP or gRPC call to the domain orchestrator’s service). This direct delegation approach is the default and recommended pattern for most scenarios. It is straightforward, low-latency, and well-supported by the LangGraph framework’s design:
Synchronous API with Asynchronous Behavior: The Global Orchestrator packages a delegation envelope (context data, allowed tools, constraints) and invokes the Domain Orchestrator’s endpoint with it. Under the hood, LangGraph’s durable execution allows the Global Orchestrator to call the domain service without blocking its own progress. The Global Orchestrator’s workflow is persisted and paused while the domain workflow runs, thanks to LangGraph’s ability to wait for external events (like a callback from the domain) before resuming. This means the Global Orchestrator is free to handle other encounters concurrently, and it will automatically resume its workflow once the Domain Orchestrator returns a result or signals completion. In essence, direct calls operate asynchronously in the context of the orchestration: the call is made, then the Global Orchestrator is idle (not consuming CPU) until the Domain Orchestrator replies.
Efficiency and Low Latency: Direct API calls avoid the extra hop and queuing overhead of a messaging layer. If a Domain Orchestrator can produce a result quickly (for example, within a few seconds), the Global Orchestrator will get the result as soon as it’s ready, enabling near real-time responses for end-to-end workflows. This is particularly important for any processes that may involve user-facing interactions or tight SLAs. The A2A protocol and our design fully support this pattern: orchestrators and agents can communicate via direct HTTP/gRPC calls, which is a well-tested approach for multi-agent workflows.
Non-Blocking and Durable: Crucially, using direct calls doesn’t compromise scalability or reliability. LangGraph’s checkpointing and callback mechanism ensure that even though the Global Orchestrator uses a “call-and-wait” pattern, it does not hold system resources during the wait. The state of the global workflow is saved to MongoDB and the orchestrator is free to do other work (or scale down) in the interim. When the Domain Orchestrator finishes (whether in milliseconds or hours later), it returns its outcome (often by invoking a callback on the Global Orchestrator or via a small response message), and the Global Orchestrator seamlessly resumes that workflow from its last checkpoint. This means direct calls are fully compatible with long-running and human-in-the-loop steps: the Global Orchestrator can wait for days if needed without any thread being blocked, because the waiting is managed via durable events in the LangGraph runtime.
Immediate Error Handling: With direct communication, error propagation is straightforward. If a Domain Orchestrator encounters a failure or cannot complete a request, it can return an error response to the Global Orchestrator (or throw an exception that the Global Orchestrator catches in its workflow logic). The Global Orchestrator then has immediate awareness of the failure and can apply its error-handling policies (such as retrying, falling back to a backup strategy, or escalating to human intervention) right away. This synchronous error feedback loop simplifies the design of compensation and retry logic since the Global Orchestrator controls the sequence of steps.
Given these characteristics, direct orchestrator-to-orchestrator calls are the norm for our design. They provide a simpler, tightly coordinated interaction, with no extra components. Thanks to the concurrency and durability of our orchestration engine, this simplicity does not hinder performance or scalability – the platform can still handle 100k+ daily encounters via direct calls, because each orchestrator service will scale out with more instances under load, and each individual instance can juggle many concurrent workflows through async I/O and state management. In essence, the default architecture assumes the Global Orchestrator will communicate with Domain Orchestrators much like function calls in a distributed system, with robust stateful management ensuring those calls don’t become a bottleneck.
Optional Integration: Azure Event Hub for Bursty or Massive Parallel Workloads
While direct calls suffice for most cases, we’ve designed the system to accommodate an event-driven communication model in scenarios where further decoupling or load leveling is needed. In particular, Azure Event Hub (or similarly, Azure Service Bus) can be introduced between the Global and Domain Orchestrators in special situations:
Handling Traffic Spikes & Burstiness: If the rate of incoming domain tasks can spike beyond what the Domain Orchestrators can instantly process, an Event Hub provides a buffering layer. The Global Orchestrator can rapid-fire publish domain task events into an Event Hub without waiting, and those events will queue up durably. The Domain Orchestrators then pull from the Event Hub at their own pace, processing tasks as they have capacity. This model ensures that sudden bursts (e.g., thousands of new claims arriving within a minute) do not overwhelm the domain services; instead, events are stored in the hub and gradually dispatched. It effectively decouples the intake of work from the processing in time, making the system more resilient to load variability. The Global Orchestrator remains responsive, as it offloads work to the Event Hub and can immediately proceed to other tasks.
Maximizing Parallelism & Throughput: When a domain workflow requires processing a very large number of parallel tasks, an Event Hub enables a scalable fan-out. In our architecture, we primarily foresee this usage within a domain’s internal steps (for example, a Domain Orchestrator might internally break a task into 50 parallel calls to downstream agents and use an Event Hub to coordinate that fan-out/fan-in). However, the same principle can be applied one level up if the Global Orchestrator needs to dispatch many domain-level tasks concurrently. By using an Event Hub, each Domain Orchestrator service auto-scales by consuming from partitions in parallel. Azure Event Hubs are designed for extremely high message throughput (millions of events per second), and by configuring a sufficient number of partitions, we allow dozens of domain orchestrator instances to fetch tasks concurrently from the stream . This yields effectively unbounded horizontal scaling for the domain processing layer – if more capacity is needed, spinning up more domain orchestrator instances will immediately increase consumption throughput (the Event Hub and Azure KEDA will distribute partitions among them). The Global Orchestrator, in this setup, behaves more like a dispatcher: it emits events and doesn’t worry about who picks them up or in what order they complete.
Loose Coupling & Independent Scaling: Introducing an Event Hub also means the Global Orchestrator and Domain Orchestrators are less directly dependent on each other’s availability. The Global Orchestrator doesn’t need to know the exact address or status of a Domain Orchestrator instance – it just sends an event to the hub. If a Domain Orchestrator service is temporarily down or scaling up, the events will patiently wait in the hub until a consumer is ready, providing a measure of fault tolerance. Each domain service can also scale or even be deployed independently, as long as it connects to the Event Hub to receive tasks. This fire-and-forget pattern can increase the overall resiliency of the system: a domain outage doesn’t block the Global Orchestrator (tasks queue up instead of failing), and a slow-down in one domain doesn’t slow the others. In practice, our A2A communication framework supports both modes – direct calls and message-based invocation – so we have the flexibility to configure domains to use events if needed.
Trade-offs of Using Event Hubs: The decision to add an Event Hub between the orchestrators should be made judiciously, since it adds complexity. Event Hubs operate on an at-least-once delivery model, so Domain Orchestrators must be designed for idempotency (handling potential duplicate events) and robust error handling. If a domain processing fails for a given event, the message may be retried or sent to a dead-letter queue; the Global Orchestrator’s workflow needs to account for the possibility that a domain response might be delayed or never returned. In contrast, with direct calls, a failure is immediately visible to the Global Orchestrator, which can then decide how to proceed (retry, alternate path, etc.) as part of its workflow logic. Additionally, latency can be slightly higher: even though Event Hubs are fast, there’s inherent overhead in the publish/consume cycle. For backend batch tasks this is usually acceptable, but for interactive or short-lived processes it could be unnecessary.
Another consideration is message ordering. With direct calls, the Global Orchestrator fully controls the sequence of domain invocations – for example, it can call Domain A then Domain B in a strict order. With an Event Hub, events are typically processed in the order they arrive within each partition, but if events span multiple partitions or multiple consumer instances, the overall processing order can become asynchronous and out-of-order. If the orchestration logic depends on ordered execution of domains, it’s better to use direct calls or ensure a single-threaded consumption (which may negate the throughput benefits of the Event Hub). If ordering is not important – or each event is independent – then the concurrency is a positive.
Observability and Correlation: Whether using direct calls or an Event Hub, our architecture maintains end-to-end traceability through consistent use of trace IDs. With direct calls, the trace context flows with the HTTP/gRPC request; with an Event Hub, we propagate the trace ID within the event metadata. In both cases, the effect is that a single OpenTelemetry trace_id links the Global Orchestrator’s steps with the Domain Orchestrator’s processing and any agent calls within, so we still get a unified view in Azure Application Insights or Arize of each encounter’s path. This means adding an Event Hub does not break our ability to monitor and debug – it just requires the discipline of passing along correlation information.
In summary, you do not need an Event Hub between the Global and Domain Orchestrators in most cases. Our baseline design uses direct orchestrator calls, which, combined with LangGraph’s durable async pattern, already achieve scalable and non-blocking behavior. However, our architecture remains flexible: if we face use-cases that involve extreme concurrency or temporal decoupling, we can incorporate Event Hubs (or Service Bus) as an additional layer to improve throughput and resiliency. The table below outlines key decision points:
Implications for Error Handling: With direct calls, the Global Orchestrator is in the call stack of the Domain Orchestrator’s execution, so errors propagate naturally. If the domain returns an error or times out, the Global Orchestrator knows immediately and can handle it (log it, retry the call, switch to a backup strategy, or raise a human intervention request as defined by the workflow). When using an Event Hub, error handling becomes event-driven: the Domain Orchestrator would likely need to send a completion event (with either a result or an error status) back to the Global Orchestrator. The Global Orchestrator’s workflow, which is waiting for a response event, must be prepared to handle a “failure” message or a timeout if no response arrives in a certain window. This shifts some error-handling complexity to a distributed model — for example, deciding how many times to retry a domain task event, or when to give up and mark the workflow as failed. Our design mitigates some of this complexity by making Domain Orchestrators themselves highly reliable (with their own retries and fallbacks internally) and by ensuring that any critical failures get surfaced in a final response event. Essentially, if a Domain Orchestrator cannot complete its task after its own error-handling attempts, it will emit a “failure result” event that the Global Orchestrator can catch and act upon. This way, even with asynchronous decoupling, we maintain clear communication about success or failure of each workflow.
Observability and Trace IDs: Whether using direct calls or an Event Hub, our orchestrators maintain end-to-end observability. As noted, we propagate a common trace_id through all steps of an encounter. In the direct-call model, this happens via standard distributed tracing of HTTP/gRPC calls. In the Event Hub model, we include the trace context in the event payload or headers; the Domain Orchestrator, upon processing the event, attaches that same trace_id to its log and telemetry emissions. This ensures that in Application Insights or Arize Phoenix, we can still see a unified timeline of the workflow across the Global Orchestrator, the Event Hub handoff, the Domain Orchestrator, and any agents it calls. The use of Event Hub does not break our logging/tracing, but it does require careful correlation logic (which we have implemented using the OTel libraries). In terms of monitoring, Azure’s tooling (Event Hub metrics, Application Insights, etc.) will allow us to keep an eye on the event queue length, ingestion rate, and processing rate – so we would set up alerts if events backed up (indicating a need to scale out domain consumers) or if processing lag grows.
Message Ordering Considerations: In direct calls, ordering is straightforward (the Global Orchestrator can enforce a strictly sequential flow among domains if needed). With an Event Hub, we get parallelism at the expense of inherent ordering. If the order in which multiple domain tasks are executed doesn’t matter (or if each request triggers exactly one domain workflow), then this isn’t an issue. But if there were a case where the Global Orchestrator would ordinarily call Domain A then Domain B in sequence (perhaps to use B’s output after A), an asynchronous approach would require rethinking: you might need to combine those into one domain orchestrator, or use an event chain (Domain A publishes an event that Domain B listens to, etc.), which complicates things. In our healthcare RCM context, most encounters are routed to one primary domain orchestrator (e.g., a claim either goes to the Claims Orchestrator or the PriorAuth Orchestrator based on context, not both in sequence), so inter-domain ordering is typically not a concern. We design domain orchestrations to be largely independent. If a use case arises where multiple domain orchestrators must work in tandem on one request, we would likely handle that within a single orchestrator (having it coordinate sub-steps for each domain) rather than firing off two unrelated events. Thus, the need for cross-domain ordering via Event Hubs is minimal in our design.
To summarize, we do not include an Azure Event Hub between the Global and Domain Orchestrators by default, because direct orchestrator calls are efficient, simpler, and sufficiently scalable given our architecture’s use of asynchronous, durable workflows. Event Hub remains an optional enhancement – a tactical addition for scenarios where extreme load or parallelism demands it. The decision can be guided by these conditions:
If we require real-time or tightly ordered orchestration and want to minimize latency and complexity, we stick to direct calls.
If we face huge surges in traffic or need to farm out massive numbers of tasks concurrently, we may introduce an Event Hub to absorb the burst and let the system scale out more gracefully.
In all cases, LangGraph’s features (checkpointing, event handling, async callbacks) and our careful state management (Redis/MongoDB) ensure that either communication mode is handled in a durable, non-blocking manner . The orchestrators will pause and resume as needed, and our monitoring will track each workflow across whichever path it takes.
By incorporating this decision logic into the design, we ensure the architecture can be adapted dynamically: deploy with the simpler direct model first, and only add the messaging layer for orchestrator-to-orchestrator calls if and when it becomes necessary. This balanced approach meets current requirements while keeping the door open for future scalability refinements, all within the robust framework of our Global Orchestrator system.
